1 SQL Injection (OWASP A03:2021)

📌 What is SQL Injection?

SQL Injection occurs when an application fails to properly sanitize user input before using it in SQL queries. Attackers can manipulate SQL queries by injecting malicious SQL code, allowing them to:

  • Bypass authentication
  • Read sensitive data
  • Modify or delete data
  • Execute administrative operations

🎯 Affected Components in JobLink Demo

Vulnerable Areas:

  • Login Form (login.html) → backend/login.php
  • Job Search (jobs.html) → backend/search.php
  • User Profile Update → backend/update_profile.php

💻 Vulnerable Code Example

// VULNERABLE - backend/login.php $email = $_POST['email']; $password = $_POST['password']; $query = "SELECT * FROM users WHERE email = '" . $email . "' AND password = '" . $password . "'"; $result = mysqli_query($conn, $query);

🚀 How to Exploit

Steps to Demonstrate SQL Injection:

  1. Go to login.html
  2. In the Email field, enter: ' OR '1'='1
  3. In the Password field, enter: anything
  4. Click Login
  5. The SQL query becomes: SELECT * FROM users WHERE email = '' OR '1'='1' AND password = 'anything'
  6. This will return all users because '1'='1' is always true!

Other Payloads to Try:

  • admin' -- (comments out the rest of the query)
  • ' OR 1=1 -- (classic SQL injection)
  • '; DROP TABLE users; -- (destructive attack)

✅ How to Fix

Recommendations:

  • Use Prepared Statements: Use parameterized queries with prepared statements (PDO or MySQLi prepared statements)
  • Input Validation: Validate and sanitize all user inputs
  • Principle of Least Privilege: Database user should have minimal required permissions
  • Error Handling: Don't expose database errors to users
  • Web Application Firewall (WAF): Deploy WAF to detect and block SQL injection attempts

Secure Code Example:

// SECURE - Using Prepared Statements $email = $_POST['email']; $password = $_POST['password']; $stmt = $conn->prepare("SELECT * FROM users WHERE email = ? AND password = ?"); $stmt->bind_param("ss", $email, $password); $stmt->execute(); $result = $stmt->get_result();

2 Broken Access Control (OWASP A01:2021)

📌 What is Broken Access Control?

Broken Access Control occurs when authorization checks are weak or missing, allowing users to access resources they shouldn't have access to. Common issues include:

  • IDOR (Insecure Direct Object References) - accessing resources by ID
  • Unprotected Admin Panels
  • No role-based access control verification
  • Missing authorization checks on API endpoints

🎯 Affected Components in JobLink Demo

Vulnerable Areas:

  • Admin Panel (admin.html) - Accessible to anyone without authentication
  • Job Edit (jobs.html?job_id=X) - Can edit any job by changing ID
  • User Profile (jobs.html?edit=X) - Can view/edit other users' profiles

💻 Vulnerable Code Example

// VULNERABLE - admin.html // NO authentication check before showing admin panel // Anyone can access this page by visiting admin.html // The page doesn't verify if user is logged in or has admin role

🚀 How to Exploit

Test 1 - Access Admin Panel Without Login:

  1. Go to admin.html
  2. You have full access to admin functions without logging in!
  3. Try clicking on "Edit" or "Delete" buttons for any user

Test 2 - IDOR on Job Editing:

  1. Go to jobs.html
  2. Click "Edit Job" on any job (e.g., job_id=1)
  3. Change the URL to different job IDs: job-edit.html?job_id=2, job-edit.html?job_id=3, etc.
  4. You can edit jobs that belong to other companies!

Test 3 - Access Other User Profiles:

  1. Try URLs like: jobs.html?user_id=1, jobs.html?user_id=2, etc.
  2. View sensitive information from other users

✅ How to Fix

Recommendations:

  • Authentication Verification: Always verify user is logged in before showing sensitive pages
  • Authorization Checks: Verify user has correct role/permissions for the resource
  • Principle of Least Privilege: Users should only access their own data
  • Role-Based Access Control (RBAC): Implement proper role hierarchy
  • Attribute-Based Access Control (ABAC): Check resource ownership
  • Server-Side Enforcement: Never rely on client-side checks only

Secure Code Example:

// SECURE - Checking authentication and authorization session_start(); if (!isset($_SESSION['user_id'])) { header('Location: login.html'); exit; } // Verify user owns this resource $user_id = $_SESSION['user_id']; $job_id = $_GET['job_id']; $stmt = $conn->prepare("SELECT owner_id FROM jobs WHERE id = ?"); $stmt->bind_param("i", $job_id); $stmt->execute(); $result = $stmt->get_result(); $job = $result->fetch_assoc(); if ($job['owner_id'] != $user_id) { header('HTTP/1.0 403 Forbidden'); exit('You do not have permission to edit this job'); }

3 Identification & Authentication Failures (OWASP A07:2021)

📌 What is Authentication Failure?

Authentication failures occur when security mechanisms that protect user accounts are weak or missing. This includes:

  • Weak or default passwords
  • Brute force attacks not prevented
  • Password not properly hashed
  • Session tokens not properly managed
  • Credentials exposed in logs or error messages

🎯 Affected Components in JobLink Demo

Vulnerable Areas:

  • Login Page - No rate limiting on failed attempts
  • Password Storage - Weak password hashing or plain text
  • Session Management - Tokens not properly validated
  • Remember Me Feature - Long session expiry without verification

💻 Vulnerable Code Example

// VULNERABLE - backend/login.php $password = $_POST['password']; // Password stored as plain text or weak hash! $query = "SELECT * FROM users WHERE email = ? AND password = '" . md5($password) . "'"; // No rate limiting - can brute force // No account lockout after failed attempts

🚀 How to Exploit

Test 1 - Try Default/Weak Credentials:

  1. Go to login.html
  2. Try common credentials:
    • admin@joblink.com / admin123
    • admin@joblink.com / password
    • employer@joblink.com / password123

Test 2 - Brute Force Attack (No Rate Limiting):

  1. The application doesn't prevent multiple login attempts
  2. An attacker could script multiple login attempts to guess passwords
  3. No CAPTCHA or account lockout mechanism

Test 3 - View Credentials in Source:

  1. View page source of admin.html
  2. Database credentials are exposed in the page!

✅ How to Fix

Recommendations:

  • Strong Password Hashing: Use bcrypt, scrypt, or Argon2 (not MD5 or SHA1)
  • Password Policy: Enforce minimum length, complexity requirements
  • Rate Limiting: Limit login attempts (5 attempts per 15 minutes)
  • Account Lockout: Lock account after N failed attempts
  • Multi-Factor Authentication: Add 2FA/MFA for additional security
  • Session Management: Short expiry times, secure tokens
  • Never Expose Credentials: Keep secrets in environment variables

Secure Code Example:

// SECURE - Using bcrypt and rate limiting require 'rate_limiter.php'; $email = $_POST['email']; // Rate limiting if (isRateLimited($email)) { http_response_code(429); die('Too many login attempts. Try again later.'); } // Get user with proper query $stmt = $conn->prepare("SELECT id, password_hash FROM users WHERE email = ?"); $stmt->bind_param("s", $email); $stmt->execute(); $result = $stmt->get_result(); $user = $result->fetch_assoc(); // Verify password with bcrypt if ($user && password_verify($_POST['password'], $user['password_hash'])) { $_SESSION['user_id'] = $user['id']; session_regenerate_id(); } else { recordFailedAttempt($email); die('Invalid credentials'); }

4 Security Misconfiguration (OWASP A05:2021)

📌 What is Security Misconfiguration?

Security Misconfiguration occurs when security settings are not properly configured, exposing sensitive information or allowing unauthorized access. Common issues include:

  • Exposed secrets (API keys, database passwords)
  • Debug information visible in errors
  • Default credentials not changed
  • Weak CORS policies
  • Directory listing enabled
  • Sensitive files accessible

🎯 Affected Components in JobLink Demo

Vulnerable Areas:

  • admin.html - Database credentials hardcoded in HTML
  • Admin Page Source - API keys and secrets in JavaScript
  • Console Logs - Debug information exposed
  • .env File (if exposed) - Environment variables visible

💻 Vulnerable Code Example

// VULNERABLE - admin.html // Hardcoded database credentials in HTML! Database Host: 192.168.199.250 Database User: root Database Password: password123 JWT Secret: super_secret_key_12345_exposed_in_source // API credentials in JavaScript const API_KEY = 'api_key_12345_exposed'; const API_URL = 'http://192.168.199.250:8000/backend/';

🚀 How to Exploit

Test 1 - Exposed Database Credentials:

  1. Open admin.html
  2. Right-click and select "View Page Source"
  3. Scroll down to "Database Configuration" section
  4. Find database credentials:
    • Host: 192.168.199.250
    • User: root
    • Password: password123
    • Database: joblink_demo
  5. Attacker can now directly access the database!

Test 2 - Exposed API Keys:

  1. Open developer console (F12) on admin.html
  2. Look for API_KEY and API_URL variables
  3. Attacker can use these credentials for unauthorized API access

Test 3 - Debug Information:

  1. Open browser console on any page
  2. Look for console.log statements with debug info
  3. Error messages expose file paths and system details

✅ How to Fix

Recommendations:

  • Environment Variables: Store secrets in .env files (never commit to git)
  • Secrets Management: Use Azure Key Vault, AWS Secrets Manager, or HashiCorp Vault
  • Remove Debug Code: Don't leave console.log or debug statements in production
  • Security Headers: Set Content-Security-Policy, X-Frame-Options, etc.
  • CORS Configuration: Restrict to trusted origins only
  • Error Handling: Don't expose stack traces or file paths to users
  • Disable Directory Listing: Prevent access to directories

Secure Code Example:

// SECURE - Using environment variables // .env file (NOT committed to git) DB_HOST=192.168.199.250 DB_USER=db_user DB_PASSWORD=secure_password_here API_KEY=secret_api_key_here JWT_SECRET=secret_jwt_key_here // backend/config.php $db_host = $_ENV['DB_HOST'] ?? getenv('DB_HOST'); $db_user = $_ENV['DB_USER'] ?? getenv('DB_USER'); $db_pass = $_ENV['DB_PASSWORD'] ?? getenv('DB_PASSWORD'); // Never expose in client-side code // Use backend API endpoints instead

5 Vulnerable & Outdated Components (OWASP A06:2021)

📌 What are Vulnerable Components?

Vulnerable Components occur when using outdated or insecure third-party libraries with known vulnerabilities. This includes:

  • Outdated versions of popular libraries
  • Dependencies with known CVEs (Common Vulnerabilities and Exposures)
  • Unmaintained or abandoned packages
  • Libraries included in production without security review

🎯 Affected Components in JobLink Demo

Vulnerable Areas:

  • jQuery 1.12.4 - Released 2016, has known XSS vulnerabilities
  • Bootstrap 3 - Outdated, multiple vulnerabilities
  • PHP Version - If using PHP < 7.4
  • MySQL Driver - Deprecated MySQLi/MySQL extensions

💻 Vulnerable Code Example

// VULNERABLE - Using outdated jQuery <script src="https://code.jquery.com/jquery-1.12.4.min.js"></script> // jQuery 1.12.4 has multiple known vulnerabilities // Released in 2016, no longer maintained // Outdated Bootstrap <link rel="stylesheet" href="bootstrap.3.3.7.min.css"> // Bootstrap 3 reached end of life

🚀 How to Exploit

Test 1 - Check for Outdated Libraries:

  1. Open page source of any page
  2. Look for script and link tags
  3. Find outdated jQuery version: 1.12.4
  4. This version is from 2016 and has known vulnerabilities!

Test 2 - Known Vulnerabilities:

  1. jQuery 1.12.4 has CVE-2020-11022 and CVE-2020-11023 (XSS vulnerabilities)
  2. Attackers could inject malicious code through jQuery selectors
  3. These vulnerabilities were fixed in jQuery 3.5.0

Test 3 - Dependency Chain:

  1. Outdated packages can pull in other vulnerable dependencies
  2. One vulnerable package can compromise the entire application

✅ How to Fix

Recommendations:

  • Audit Dependencies: Use npm audit, composer audit, or similar tools
  • Update Regularly: Keep all dependencies up to date
  • Monitor for CVEs: Use tools like Snyk, Dependabot, or OWASP Dependency-Check
  • Remove Unnecessary: Only include required dependencies
  • Software Bill of Materials (SBOM): Track all components and versions
  • Automated Testing: Integrate security scanning in CI/CD pipeline
  • Use Security Tools: npm audit, Snyk, Black Duck, WhiteSource

Secure Code Example:

// SECURE - Using modern versions // package.json { "dependencies": { "jquery": "^3.7.0", // Latest stable version "bootstrap": "^5.3.0", // Latest Bootstrap 5 "axios": "^1.4.0" } } // Run: npm audit fix // This will update vulnerable packages // .github/workflows/security.yml (CI/CD scanning) - name: Run npm audit run: npm audit --audit-level=moderate - name: Check with Snyk run: snyk test
